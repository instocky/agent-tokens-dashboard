# PRD: Token Usage Dashboard Prototype

## 1. Summary

Локальный прототип статического дашборда для визуализации расхода токенов из `runtime-state.sqlite`.

Цель прототипа: быстро получить читаемый локальный dashboard без постоянного web-сервиса, с автообновлением каждые 5 минут через Windows Task Scheduler.

## 2. Product Goal

Дать владельцу локальный, быстро открываемый dashboard, который показывает:

- расход токенов за текущий календарный час
- расход токенов с начала суток (00:00 — текущий час включительно)
- расход токенов в активном 5-часовом слоте (см. §6.3)
- распределение токенов по часам внутри активного слота
- сравнение последних 4 недель по дням недели

## 3. Non-Goals

В прототип не входят:

- FastAPI, Flask или любой постоянно работающий backend
- realtime через websocket или SSE
- multi-user доступ
- публикация на сервер
- отдельный JSON API
- учёт `cache_read_tokens` и `cache_write_tokens` в основной метрике
- анализ стоимости как главного KPI

## 4. Users

Один локальный пользователь на одной Windows-машине.

## 5. Source of Truth

Источник данных: `local_runtime_token_usage` в файле `runtime-state.sqlite`.

Основная метрика:

- `tokens = input_tokens + output_tokens`

Не включать в основную метрику:

- `cache_read_tokens`
- `cache_write_tokens`
- `reasoning_tokens`
- `cost_usd`

## 6. Data Rules

### 6.1 Timezone

Все агрегаты считаются в timezone `Europe/Moscow`.

### 6.2 Calendar Hour

Все почасовые расчёты считаются по календарному часу:

- начало часа: `HH:00:00`
- конец часа: `HH:59:59`

### 6.3 Active Window (5-часовые слоты)

В прототипе используется **скользящее 5-часовое окно**, привязанное к
текущему часу. Слот выбирается из таблицы, а не считается от текущего
часа непрерывно — это держит лейблы стабильными (на 14:30 окно то же,
что в 13:00) и легко читается на UI.

Слоты (half-open по верхней границе):

| Слот       | Часы (UTC+3)        | Лейбл           |
|------------|---------------------|-----------------|
| Утро       | `[3, 8)`  → 03-07   | `03:00–07:59`   |
| День       | `[8, 13)` → 08-12   | `08:00–12:59`   |
| После обеда| `[13, 18)` → 13-17  | `13:00–17:59`   |
| Вечер      | `[18, 23)` → 18-22  | `18:00–22:59`   |
| Ночь       | `[23, 3)` → 23+0-2  | `23:00–02:59`   |

**Ночной слот — 4 часа, переход через полночь.** Это сознательный
компромисс: честное окно `23:00–02:59` важнее, чем добивать до 5
часов через `22:00` или `03:00`. Данные для ночного слота собираются
с двух дат: час `23:00` берётся из (сегодня − 1 день), часы `00-02` — из сегодня.

**Правила выбора слота:**

- слот определяется по `now.hour` (MSK) и не меняется внутри слота
- слот переключается ступенчато в `03:00 / 08:00 / 13:00 / 18:00 / 23:00`
- для дневных слотов все 5 часов — из сегодняшней даты
- для ночного слота — `23:00` вчера + `00-02` сегодня

**Сумма и разбивка:**

- карточка показывает общую сумму токенов за слот
- мини-бары под карточкой — почасовая разбивка в порядке часов слота
- для ночного слота — 4 мини-бара (`23, 00, 01, 02`); в title бара
  указана конкретная дата, чтобы было видно переход через полночь

### 6.4 Weekly Chart

График должен показывать последние 4 недели по абсолютным номерам недель:

- пример для даты `2026-08-03`: `W-29`, `W-30`, `W-31`, `W-32`

Правила отображения:

- каждая неделя отображается как отдельная группа
- внутри группы 7 столбцов: `Пн`, `Вт`, `Ср`, `Чт`, `Пт`, `Сб`, `Вс`
- текущая неделя допускается неполной
- будущие дни текущей недели не отображаются как `0`
- будущие дни текущей недели отображаются как disabled / no data yet

### 6.5 Weekly Cap Threshold

Контракт недельной квоты (`weekly_cap`) на input+output токены. На текущий день
weekly chart рисуется горизонтальная пунктирная линия красного цвета с
подписью «порог N.NNM» — это «потолок» сегодняшнего расхода, ниже которого
нужно остаться, чтобы уложиться в капу за 7 дней (включая сегодня).

**Формула** (целочисленная, floor вниз):

```
threshold_today = max(0, (weekly_cap − today_spent) / days_left)
days_left = 8 − isoweekday(today)         # Пн=7, Вт=6, …, Вс=1
```

**Семантика «превышения»:**

- если `today_spent > threshold` — бар визуально выше линии, и на следующий
  день формула пересчитается (новые `today_spent` и `days_left` → новый
  threshold). Это и есть «если превысил — на следующий день уровень
  пересчитается».
- если `today_spent ≥ weekly_cap` (вся неделя уже превышена) — threshold = 0,
  линия прижата к низу бара.
- если `days_left ≤ 0` (теоретически не возникает, защита от деления на 0) —
  threshold не рисуется.

**Default `weekly_cap = 75 000 000` токенов**, константа `WEEKLY_CAP_TOKENS`
в `build_dashboard.py`. Изменяется в одном месте; не env, не CLI — это
бизнес-лимит, а не runtime-параметр.

### 6.6 Today · 24H Stream (почасовая разбивка)

Карточка показывает расход токенов за каждый час текущего MSK-дня (00..23)
в виде 24 баров. Цель — at-a-glance pattern recognition: когда был пик, на
каком уровне текущий час, где провалы.

**Состояния баров:**

| `state`    | Когда                                                      | Визуал                                  |
|------------|------------------------------------------------------------|-----------------------------------------|
| `active`   | `h < now.hour` и `value > 0`                               | Зелёный по квартилю интенсивности (L1..L4) |
| `peak`     | Топ-1 по `value` среди `h <= now.hour`                     | Яркий `#00d97e` + glow                  |
| `current`  | `h == now.hour` (если не peak)                             | Тот же цвет по квартилю + outline 1px   |
| `empty`    | `h < now.hour` и `value == 0`                              | 2px нейтральный floor                   |
| `future`   | `h > now.hour`                                             | Пунктир, opacity 0.55                   |

**Гамма интенсивности** — GitHub contribution palette, 4 уровня:

| Уровень | Цвет     | Квартиль (среди ненулевых `active`+`current`) |
|---------|----------|----------------------------------------------|
| L1      | `#9be9a8`| ≤ Q1                                        |
| L2      | `#40c463`| ≤ Q2                                        |
| L3      | `#30a14e`| ≤ Q3                                        |
| L4      | `#216e39`| > Q3                                        |
| peak    | `#00d97e`| (вне шкалы)                                 |

Если ненулевых часов меньше 4 — все они идут в L2 (избегаем визуального
разрыва на 1-3 точках). Границы считаются по позициям в отсортированном
массиве, inclusive: `q1 = sorted[n//4]`, `q2 = sorted[n//2]`,
`q3 = sorted[(3n)//4]`. `value <= q1 → L1`, ..., `value > q3 → L4`.

**NOW marker:** удалён (TL review, 2026-08-04). Текущий час визуально
отличается тонким outline (.bar-24h.current), а позиция «сейчас» читается
из meta-строки `Всего · Пик: HH:00` (running total до текущего часа
включительно однозначно фиксирует, какой час последний). Бейдж `NOW` на
24-барной карточке создавал визуальный шум и дублировал то, что уже
видно из meta + outline.

**Легенда:** формат GitHub contribution heatmap — `Less [L1][L2][L3][L4] More`,
только шкала интенсивности. Состояния баров (`empty` / `future` / `peak` /
`current`) читаются напрямую из их собственного стиля (пунктир / 2px floor /
яркий accent / outline) и в легенде не перечисляются, чтобы не дублировать.

**Метаданные карточки (правый верх):** `Всего: {fmt_tokens(sum)} · Пик: HH:00 ({fmt_tokens(peak_val)})`.
Никаких переключателей шкалы (линейная/лог) — это распределение по часам,
не накопительная метрика.

**Чистая функция:** `compute_today_24h(hourly, now_msk) -> list[HourlyBar]`,
где `HourlyBar = (hour, value, state, intensity)`. Тесты в
`tests/test_24h_stream.py` (15 кейсов: state machine, peak selection,
quartile distribution, current==peak boundary, empty/future semantics).

## 7. UX Requirements

### 7.1 Delivery Model

Продукт поставляется как один self-contained файл:

- `dashboard.html`

Файл должен открываться локально через браузер без backend-сервиса и без загрузки внешнего JSON.

### 7.2 Update Model

Двухуровневое обновление:

- **Данные** (SQLite → HTML): каждые 5 минут через Windows Task Scheduler
  (`build_dashboard.py` → `dashboard.html` атомарно).
- **UI freshness** (HTML → браузер): каждые 60 секунд через
  `<meta http-equiv="refresh" content="60">` в `<head>`. Гарантирует, что
  последний билд всегда виден без ручного F5, без websocket и без
  постоянного процесса в памяти.

`refresh-dashboard.cmd` — one-click rebuild для отладки/ручного запуска
(Explorer / Start / taskbar); не часть шедулера, дополнительный путь.

### 7.3 Visual Direction

Dashboard должен сразу выглядеть как аккуратный визуальный артефакт, а не как технический отчёт.

Требования:

- спокойная, намеренная визуальная система
- компактный layout без лишней высоты
- основной фокус на weekly chart
- weekly chart в формате grouped bars
- группировка bars по неделям, не по дням

### 7.4 Dashboard Blocks

На первом экране должны быть:

- карточка `Токены / текущий час`
- карточка `Токены / сегодня` — running total с 00:00 до текущего часа
  включительно; сознательно дублирует часть графика окна, запрошена TL
- карточка `Токены в окне {label}` где `{label}` — лейбл активного слота
  (`03:00–07:59` / `08:00–12:59` / `13:00–17:59` / `18:00–22:59` /
  `23:00–02:59`); для ночного слота подпись уточняет, что данные идут
  с 23:00 вчера по 02:59 сегодня
- полоски по часам активного слота внутри или рядом с карточкой окна
  (5 баров для дневных слотов, 4 бара для ночного)
- основной weekly chart за 4 недели
- на текущем дне текущей недели — красная пунктирная линия с подписью
  «порог N.NNM» (weekly cap threshold, см. §6.5); рисуется как на
  линейной, так и на log шкале
- карточка `Today · 24H Stream` — почасовая разбивка сегодняшнего дня
  (24 бара 00..23, шкала интенсивности по GitHub-палитре,
  мета «Всего · Пик: HH:00 (N.NNM)»); см. §6.6

### 7.5 Weekly Cap Threshold

Визуально:

- красная пунктирная линия (`border-top: 2px dashed #ef4444`), ширина —
  чуть шире бара (на 3px в каждую сторону), позиционирована абсолютно
  внутри `.bar-cell` через `bottom: X%`, где `X` — тот же процент, что
  высота бара с `value = threshold` (то есть линия и бар используют одну
  шкалу — корректно на обоих вариантах linear/log)
- подпись `порог N.NNM` шрифтом 10px справа от линии, цветом `#ef4444`
- на ширине ≤ 980px подпись прячется (линия остаётся)
- в legend добавляется третий пункт: «порог недели (75 000 000 токенов)» с
  миниатюрным пунктирным маркером

Threshold рисуется ТОЛЬКО для текущего дня текущей недели. Для будущих
дней и прошлых недель линии нет.

## 8. Functional Requirements

### FR-1. Static Build

Система должна иметь Python-скрипт, который генерирует полный `dashboard.html` из SQLite.

### FR-2. Local Read

Скрипт должен читать SQLite напрямую через Python `sqlite3`, без вызова внешнего `sqlite3.exe`.

### FR-3. Current Hour Card

Скрипт должен вычислять и рендерить токены за текущий календарный час в `Europe/Moscow`.

### FR-3a. Today Card

Скрипт должен вычислять и рендерить токены с начала суток (00:00 MSK)
до текущего часа включительно — running total за сегодняшнюю дату.
Значение включает in-progress current_hour и обновляется каждый ребилд.

### FR-4. Active Window Card

Скрипт должен вычислять и рендерить для активного 5h-слота (см. §6.3):

- общий объём токенов в слоте
- разбивку по каждому часу слота
- лейбл слота в формате `HH:00–HH:59` в заголовке карточки
- для ночного слота — подпись `с 23:00 вчера по 02:59 сегодня`

### FR-5. Weekly Comparison Chart

Скрипт должен вычислять для последних 4 недель дневные суммы токенов и рендерить их как grouped bar chart:

- x-axis верхнего уровня: недели
- внутри каждой недели: `Пн ... Вс`

### FR-6. Future Days Rendering

Будущие дни в текущей неделе должны рендериться визуально как disabled, а не как реальный ноль.

### FR-7. Self-Contained Output

Все данные для рендера должны быть встроены в `dashboard.html`.

### FR-8. Weekly Cap Threshold

Скрипт должен вычислять и отображать на текущем дне текущей недели
weekly chart «потолок» сегодняшнего расхода (см. §6.5):

- `threshold = max(0, (WEEKLY_CAP_TOKENS − today_spent) / days_left)` —
  целочисленно, с floor вниз; `days_left = 8 − isoweekday(today)`
- если `days_left ≤ 0` — threshold не рисуется
- если `today_spent ≥ WEEKLY_CAP_TOKENS` — threshold = 0
- порог должен быть виден на обоих вариантах шкалы (linear / log),
  позиционироваться с тем же процентом высоты, что и бар с
  `value = threshold`
- `WEEKLY_CAP_TOKENS = 75_000_000` — константа в `build_dashboard.py`
  (бизнес-лимит, не env/CLI)
- чистая функция `compute_weekly_threshold(weekly_cap, today_spent, days_left)
  → int | None` обязана быть покрыта тестами в `tests/test_weekly_cap.py`

### FR-9. Today · 24H Stream Card

Скрипт должен вычислять и рендерить карточку `Today · 24H Stream` —
почасовую разбивку сегодняшнего MSK-дня (24 бара, часы 00..23):

- `compute_today_24h(hourly, now_msk) -> list[HourlyBar]` — чистая функция,
  возвращает 24 `HourlyBar = (hour, value, state, intensity)` с уже
  размеченными state и intensity; тесты в `tests/test_24h_stream.py`
- state-машина: `active` / `current` / `peak` / `empty` / `future` —
  правила см. §6.6
- peak — топ-1 по `value` среди `h <= now.hour`; если `current_hour` оказался
  максимумом — он же и `peak` (state=`peak`, intensity не используется —
  рендер применяет `.bar-24h.peak` без `.intensity-*`)
- intensity-квартили: 4 уровня GitHub-палитры (L1..L4) по позициям в
  отсортированном массиве ненулевых значений; при N<4 все non-zero часы
  идут в L2 (см. §6.6)
- рендер включает 24 `.hour-cell` с `.bar-24h` (state + intensity) +
  `.hour-label` (шрифт как у дней недели: Inter 12px, `var(--muted)`);
  NOW-маркер не рисуется (TL review 2026-08-04, см. §6.6) — текущий час
  отмечен тонким outline `.bar-24h.current`, а позиция «сейчас» однозначно
  читается из meta-строки
- легенда под заголовком — в формате GitHub contribution heatmap:
  `Less [L1][L2][L3][L4] More` (4 квадрата палитры, лейблы `Less`/`More` по
  краям); `active` / `peak` / `future` / `current` в легенде не перечисляются —
  эти состояния читаются напрямую из стилей баров, дублировать в легенде
  не нужно
- meta в правом верхе карточки: `Всего: {fmt_tokens(total)} · Пик: HH:00 ({fmt_tokens(peak)})`
- чистая функция `compute_today_24h` обязана быть покрыта тестами
  в `tests/test_24h_stream.py` (≥ 10 кейсов: state machine на границах,
  peak selection, current==peak, quartile distribution, empty/future
  semantics, intensity collapse при N<4)

## 9. Non-Functional Requirements

- локальный запуск на Windows
- время сборки должно быть комфортным для запуска раз в 5 минут
- чтение должно использовать короткоживущее SQLite-соединение
- решение не должно требовать постоянного процесса в памяти
- код должен быть достаточно простым для дальнейшей доработки

## 10. Proposed Technical Design

Артефакты прототипа:

- `build_dashboard.py`
- `dashboard.html`

Поток:

1. Scheduler запускает `build_dashboard.py`
2. Скрипт читает `runtime-state.sqlite`
3. Скрипт считает агрегаты
4. Скрипт встраивает данные в HTML
5. Скрипт перезаписывает `dashboard.html`

## 11. Success Criteria

Прототип считается успешным, если:

- файл `dashboard.html` открывается локально без сервера
- данные обновляются каждые 5 минут через scheduler
- weekly chart визуально читается лучше, чем текущие CLI-отчёты
- пользователь может быстро увидеть активность по текущему часу, активному 5-часовому слоту и неделям

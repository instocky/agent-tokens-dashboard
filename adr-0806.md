# ADR-001 (v2.1): Разделение `build_dashboard.py` на три слоя (analytics / render / entry)

**Статус:** утверждён, к исполнению.
**Версия:** v2.1 — правки поверх v2: правило 8 в §2.2 (граница импортов render → analytics), `pill_level` едет в snapshot (§2.3, §2.4), расширен скоуп §3 (test_today_meta / test_session_title / test_hero_pill), регламент детерминизма demo_24h для байт-идентичности, отдельный тикет на TD-2 в §6, триггер `wc -l analytics.py > 1300` как gate после шага 3.
**Область:** только рефакторинг. Новая функциональность (ежедневная аналитика, второй HTML, JSON) в объём этого изменения **не входит**.

---

## 1. Контекст

`build_dashboard.py` (~2300 строк) смешивает три ответственности: доступ к SQLite, бизнес-логику (compute) и представление (HTML/CSS/JS). Появился второй потребитель вычислений (планируемый `analytics.html` с дневными срезами за 4 недели). Копировать compute-функции недопустимо; оставлять монолит — значит умножать связность с каждым новым представлением.

Более сложные варианты (пакеты `core/`/`domain/`, классы-Builder'ы, Writer'ы, dataclass-Snapshot) рассмотрены и **сознательно отклонены** как architecture astronautics: проект ~2300 строк не требует 15 файлов. Принята минимальная структура: три модуля по трём ответственностям.

## 2. Решение

### 2.1 Целевая структура

```
build_dashboard.py      # entry: CLI + оркестрация + лог + запись файла
analytics.py            # Database Access + Business Logic + Formatting + Snapshot Builder
render_dashboard.py     # render(snapshot) -> str  (HTML + inline CSS/JS)
```

Позже (отдельные задачи, вне этого ADR): `render_analytics.py`, `build_analytics.py`, при необходимости `export_json.py`.

### 2.2 Правила слоёв

1. `render_*` **никогда** не открывает SQLite и не импортирует функции доступа к БД.
2. `analytics` **никогда** не генерирует HTML/CSS/JS-строк.
3. `build_*` (entry) содержит только CLI, оркестрацию, логирование и запись файла — никакой бизнес-логики.
4. Snapshot (обычный вложенный `dict`) — **единственный** контракт между analytics и render. `render()` принимает ровно один аргумент.
5. Любой будущий вид (второй HTML, JSON, CSV) потребляет snapshot, а не БД.
6. Новый модуль/абстракция появляются только тогда, когда их отсутствие **уже мешает**. Триггеры будущего роста: `analytics.py` ≥ 1500–2000 строк → распил по секциям на пакет `analytics/`; третий потребитель → dataclass вместо dict.
7. **Перенос по ответственности, а не механическое копирование.** Если при переносе очевидно, что функция логически относится к другому разделу — она едет туда (примеры: `project_title_from_path` и `pill_level` — бизнес-логика, а не «форматирование», хотя в старом файле лежали рядом с `fmt_*`; `_bar_height_pct`/`_y_*` — геометрия представления → `render_dashboard.py`).
8. **Импорт `render_*` из `analytics` ограничен: константы, доменные типы (`Week`, `HourlyBar`) и форматирующие хелперы `fmt_*`.** Compute, доступ к БД и бизнес-правила — только через snapshot. Допустимый пример: `from analytics import WEEKDAY_LABELS, fmt_tokens`. Недопустимый: `from analytics import compute_today`. Направление импорта однонаправленное `render → analytics`; обратное — запрещено.

### 2.3 Внутренняя архитектура `analytics.py`

Новых файлов внутри не создаём, но файл сразу имеет именованные секции — через полгода его можно будет распилить по границам секций без перемешивания:

```python
# ------------------------------------------------------------------
# Constants & Domain Types
# ------------------------------------------------------------------
# ------------------------------------------------------------------
# Database Access
# ------------------------------------------------------------------
# ------------------------------------------------------------------
# Business Logic
# ------------------------------------------------------------------
# ------------------------------------------------------------------
# Formatting Helpers
# ------------------------------------------------------------------
# ------------------------------------------------------------------
# Snapshot Builder
# ------------------------------------------------------------------
```

**Constants & Domain Types:** `MSK`, `WINDOWS`, `NIGHT_SLOT`, `WEEK_COUNT`, `WEEKDAY_LABELS`, `WEEKLY_CAP_TOKENS`, `_HOUR_STATE_LEVELS`, `_SESSION_RECORD_PATH_KEY`, `_SESSION_RECORD_TITLE_KEY`; dataclass'ы `Week`, `HourlyBar`.

**Database Access** (только SQL и извлечение сырых данных; гибридные SQL+логика функции остаются здесь до роста файла — расчленение не входит в задачу):
`open_db`, `aggregate_by_hour`, `compute_today_meta`, `compute_current_session`, `_fetch_session_path`, `_fetch_session_title`.

**Business Logic:**
`compute_current_hour`, `compute_today`, `current_window`, `compute_current_window`, `compute_weekly`, `compute_weekly_threshold`, `_intensity_level`, `compute_today_24h`, `today_24h_peak`, `compute_sparkline_*`, `compute_prev_*`, `project_title_from_path`, `pill_level` (последние две — по правилу 7, из старого «форматного» соседства). `pill_level` — пороговое бизнес-правило (80/100), вызывается **только** из `build_snapshot`, не из render (правило 8 + см. §2.4).

**Formatting Helpers:**
`fmt_tokens`, `fmt_log_tick`, `fmt_avg`, `fmt_int`, `fmt_delta_pct`, `fmt_duration`.

**Snapshot Builder:**
`build_snapshot(db_path: Path, now_msk: datetime | None = None) -> dict`. Собирает секции `hour / today / window / weekly / session` (см. §2.4); `pill_level` зовётся внутри для `session.level` и `weekly.day_level`.

**`render_dashboard.py`**
- Шкалы/геометрия: `_y_max_for`, `_y_ticks_for_log`, `_bar_height_pct` (считаются рендером из `snapshot["weekly"]["weeks"]`)
- Разметка: `_render_sparkline` (резерв), `_axis_labels_linear`, `_axis_labels_log`, `_render_weekly_grid`, `_render_24h_stream`, `_build_hero_pill_inner`, `_render_hero_pill`, `_render_combined_session_pill`, `_render_hero_pills`
- `render_html(...25 kwargs...)` → `render(snapshot: dict) -> str`
- Весь inline CSS и JS без изменений; презентационные константы `GITHUB_PALETTE` (и импорт `WEEKDAY_LABELS` из `analytics`)

**`build_dashboard.py`**
- `DB_PATH`, `OUTPUT_PATH`, `parse_args` (имена файлов и флаги CLI **не меняются**)
- `main()`: `snapshot = analytics.build_snapshot(args.db)` → лог **из полей snapshot** → `html = render_dashboard.render(snapshot)` → запись/stdout

### 2.4 Контракт snapshot (вложенный, по разделам)

Плоского словаря на 40 ключей **нет** — данные сгруппированы логически. `build_snapshot` собирает каждую секцию отдельным локальным dict'ом и возвращает `return {"now_msk": ..., "hour": hour, "today": today, ...}` — без литерала на 100 строк.

```python
snapshot = {
    "now_msk": datetime,                 # единственный временной якорь билда
    "hour": {
        "tokens": int,                   # текущий календарный час (MSK)
    },
    "today": {
        "tokens": int,                   # running total с 00:00 MSK
        "sessions": int,
        "user_requests": int,
        "avg": float,                    # user_requests / sessions
        "avg_tokens_per_session": int | None,
        "bars_24h": list[HourlyBar],
        "peak_24h": tuple[int, int] | None,   # (peak_hour, peak_value)
    },
    "window": {                          # активный 5h-слот
        "total": int,
        "entries": list[tuple[int, int, date]],  # (hour, tokens, date)
        "label": str,
        "wraps": bool,
    },
    "weekly": {
        "since": date,                   # понедельник W−3 (старт окна агрегации)
        "weeks": list[Week],
        "cap": int,                      # WEEKLY_CAP_TOKENS (для tooltip/pill)
        "today_spent": int,              # диагностические поля для лога entry
        "days_left": int,
        "threshold": int | None,         # потолок расхода на сегодня
        "day_level": str,                # pill_level(today_spent, threshold) — ok|warn|over|none
    },
    "session": {                         # самая свежая сессия за сегодня
        "id": str | None,
        "tokens": int,
        "requests": int,
        "path": str | None,
        "project_title": str | None,     # project_title_from_path(path)
        "record_title": str | None,      # record_json.title
        "duration_ms": int | None,
        "level": str,                    # pill_level(tokens, WEEKLY_CAP_TOKENS) — ok|warn|over|none (см. §2.4.1)
    },
}

### 2.4.1 Семантика `session.level`

`session.level` — pill для **текущей** сессии (HERO-pill в шапке). Сравнение
идёт против `WEEKLY_CAP_TOKENS` (60M), **не** против `avg_tokens_per_session`.

Почему не average: "average" — moving target, и "session 5× ваш обычный" не
имеет однозначного UX-смысла (плохо или хорошо?). Pill — про budget: видит ли
пользователь, что текущая сессия расходует значимую долю недельного лимита.
Сегодняшняя `current_session_tokens` (50K в demo) всегда `ok` против 60M —
это корректно: одна сессия не съедает бюджет, бюджет расходуется за неделю.

Production: `analytics.build_snapshot` вычисляет `session.level` так по построению
(analytics.py — `pill_level(current_session_tokens, WEEKLY_CAP_TOKENS)`).
Demo (`demo_24h.py`) собирает snapshot руками; должен использовать тот же cap.

```

Расчёт `since` и `threshold` (включая `today_spent`/`days_left`) живёт внутри `build_snapshot`; entry лишь логирует готовые поля — бизнес-логики в entry нет (правило 3).

### 2.5 Technical debt (осознанный долг, заморожен на время рефакторинга)

Это **не баги и не случайности**, а зафиксированный долг: поведение заморожено для побайтовой идентичности, фиксация — отдельными изменениями **после** рефакторинга.

- **TD-1.** `DB_PATH` определён дважды, вторая строка побеждает. Долг: мёртвая первая строка. Не трогаем: эффективное значение должно сохраниться.
- **TD-2.** `_render_weekly_grid` использует `date.today()` (локальная TZ машины) вместо `now_msk` из snapshot. Долг: потенциальный раскол суток при локальной TZ ≠ MSK. Не трогаем: байт-идентичность выхода важнее; фиксировать отдельным коммитом с отдельной приёмкой.
- **TD-3.** Sparklines/дельты вычисляются (`compute_sparkline_*`, `compute_prev_*`, `fmt_delta_pct`), но не рендерятся с редизайна 2026-08-04. Долг: мёртвый код в Business Logic/Formatting. Не трогаем: функции остаются как резерв, в snapshot и render не входят; удаление — отдельное решение.
- **TD-4.** Все строки HTML/CSS/JS, включая комментарии и пробелы, переносятся как есть (в том числе закомментированные `# color:` в CSS). Долг: исторические комментарии. Не трогаем: чистка меняет байты выхода.

## 3. План миграции и приёмка

**Шаг 1.** Создать `analytics.py` (перенос по секциям из §2.3 + `build_snapshot`). `build_dashboard.py` временно продолжает держать render, но импортирует перенесённое из `analytics`. Импорты в `tests/test_windows.py`, `test_24h_stream.py`, `test_weekly_cap.py`, `test_log_scale.py` (частично), `test_today_meta.py`, `test_session_title.py`, `test_hero_pill.py` (только `pill_level` — `_build_hero_pill_inner` остаётся в `build_dashboard.py` до шага 2) → `analytics.*`. Полный скоуп — 7 тестовых файлов + `demo_24h.py` (его `compute_*` импорты тоже → `analytics.*`; конвертация demo на `render(snapshot)` — шаг 2).
**Шаг 2.** Создать `render_dashboard.py`; `render_html` → `render(snapshot)`; `build_dashboard.py` становится тонким entry; `demo_24h.py` переводится на `render(snapshot)` (вместо ручного прогона pipeline + monkey-patch `bd.datetime.now(MSK)`). Импорты render-части `test_log_scale.py`/`test_weekly_cap.py`/`test_hero_pill.py` (оставшаяся часть) → `render_dashboard.*`.
**Шаг 3.** Обновить README («Project layout»).

Приёмка каждого шага:
1. Все 7 тест-файлов проходят (45 проверок суммарно — счёт сохранён, см. §3 шаг 1).
2. Эталон до старта: сохранить текущий `tmp/dashboard_demo.html`; после каждого шага выход `demo_24h.py` **побайтово идентичен**. **Регламент детерминизма:** эталон регенерируется непосредственно перед сравнением в ту же минуту (TD-2: `_render_weekly_grid` вшивает `date.today()`, байт-идентичность живёт в пределах календарных суток). Полный детерминизм — после отдельного тикета fix TD-2 (см. §6).
3. Боевая БД: `python build_dashboard.py --no-write` до/после в одну минуту → вывод идентичен (при прогонах в разные минуты допустимо расхождение только в строке «Обновлено:»).
4. `refresh-dashboard.cmd` и задача Task Scheduler работают без правок.
5. Stdlib only, Python 3.9+, `from __future__ import annotations` в новых модулях.
6. После шага 1: `python -c "import analytics, build_dashboard"` без ошибок. После шага 2: то же + `import render_dashboard` — ловит циклические импорты до прогона тестов.

## 4. Анти-требования (не делать)

- ❌ пакеты и каталоги (`analytics/`, `core/`, `domain/`, `readers/`, `writers/`, `engine/`, `formatters/`); новые файлы сверх трёх из §2.1;
- ❌ классы-Builder'ы, dataclass-Snapshot, Writer-абстракции;
- ❌ плоский snapshot на 40 ключей — только группировка из §2.4;
- ❌ JSON/экспорт в этой задаче;
- ❌ любые правки HTML/CSS/JS, «улучшения» и чистки (включая TD-1, TD-3, TD-4);
- ❌ переименование entry-файла и флагов CLI;
- ❌ новая compute-логика: рефакторинг — перенос по ответственности (правило 7), а не переписывание;
- ❌ механическое копирование кусков файла без присвоения секции.

## 5. Последствия

**+** Второй вид подключается без дублирования compute; `build_dashboard.py` снижается до ~120 строк; тесты проверяют слои раздельно; `analytics.py` с именованными секциями готов к будущему распилу без перемешивания; snapshot читается как `analytics.today.tokens`, а не как `snapshot["today_tokens"]`.
**−** Контракт snapshot не проверяется типами (dict) — компенсируется тестами и §2.4; при третьем потребителе заменить на dataclass (триггер из §2.2, правило 6).

## 6. Будущая работа (вне этого ADR, для контекста)

1. Ежедневная аналитика за 4 недели: daily-запросы в Database Access, daily-секция snapshot, `render_analytics.py`, `build_analytics.py`, `analytics.html`. JSON — только при появлении потребителя, как сериализация snapshot (`export_json.py`).
2. Распил `analytics.py` на пакет `analytics/` по границам секций. **Триггер:** замер `wc -l analytics.py` сразу после шага 3; если > 1300 — отдельный тикет, не оставлять «на потом».
3. Фиксация TD-1, TD-3, TD-4 отдельными изменениями.
4. **TD-2 — отдельный тикет, вне общей кучи.** `_render_weekly_grid` использует `date.today()` (локальная TZ машины) вместо `now_msk` из snapshot → раскол суток на хостах с TZ ≠ MSK. Фикс: `_render_weekly_grid` принимает `snapshot["now_msk"]` и `snapshot["weekly"]["since"]`, считает индекс «сегодня» из них. Блокирует полную байт-идентичность `tmp/dashboard_demo.html` через сутки (см. §3 регламент детерминизма).
5. Беклог: индекс `local_runtime_message_rows(created_at_ms)`.

# PRD: Token Usage Dashboard Prototype

## 1. Summary

Локальный прототип статического дашборда для визуализации расхода токенов из `runtime-state.sqlite`.

Цель прототипа: быстро получить читаемый локальный dashboard без постоянного web-сервиса, с автообновлением каждые 5 минут через Windows Task Scheduler.

Дата фиксации PRD: 2026-08-03.
Изменения: 2026-08-03 — §6.2/§6.3/§7.4 — окно 03-07 заменено на скользящее 5-часовое (5 слотов).

## 2. Product Goal

Дать владельцу локальный, быстро открываемый dashboard, который показывает:

- расход токенов за текущий календарный час
- расход токенов в активном 5-часовом слоте (см. §6.3)
- распределение токенов по часам внутри активного слота
- сравнение последних 4 недель по дням недели

## 3. Non-Goals

В прототип не входят:

- FastAPI, Flask или любой постоянно работающий backend
- realtime через websocket или SSE
- multi-user доступ
- публикация на сервер
- отдельный JSON API
- учёт `cache_read_tokens` и `cache_write_tokens` в основной метрике
- анализ стоимости как главного KPI

## 4. Users

Один локальный пользователь на одной Windows-машине.

## 5. Source of Truth

Источник данных: `local_runtime_token_usage` в файле `runtime-state.sqlite`.

Основная метрика:

- `tokens = input_tokens + output_tokens`

Не включать в основную метрику:

- `cache_read_tokens`
- `cache_write_tokens`
- `reasoning_tokens`
- `cost_usd`

## 6. Data Rules

### 6.1 Timezone

Все агрегаты считаются в timezone `Europe/Moscow`.

### 6.2 Calendar Hour

Все почасовые расчёты считаются по календарному часу:

- начало часа: `HH:00:00`
- конец часа: `HH:59:59`

### 6.3 Active Window (5-часовые слоты)

В прототипе используется **скользящее 5-часовое окно**, привязанное к
текущему часу. Слот выбирается из таблицы, а не считается от текущего
часа непрерывно — это держит лейблы стабильными (на 14:30 окно то же,
что в 13:00) и легко читается на UI.

Слоты (half-open по верхней границе):

| Слот       | Часы (UTC+3)        | Лейбл           |
|------------|---------------------|-----------------|
| Утро       | `[3, 8)`  → 03-07   | `03:00–07:59`   |
| День       | `[8, 13)` → 08-12   | `08:00–12:59`   |
| После обеда| `[13, 18)` → 13-17  | `13:00–17:59`   |
| Вечер      | `[18, 23)` → 18-22  | `18:00–22:59`   |
| Ночь       | `[23, 3)` → 23+0-2  | `23:00–02:59`   |

**Ночной слот — 4 часа, переход через полночь.** Это сознательный
компромисс: честное окно `23:00–02:59` важнее, чем добивать до 5
часов через `22:00` или `03:00`. Данные для ночного слота собираются
с двух дат: час `23:00` берётся из (сегодня − 1 день), часы `00-02` — из сегодня.

**Правила выбора слота:**

- слот определяется по `now.hour` (MSK) и не меняется внутри слота
- слот переключается ступенчато в `03:00 / 08:00 / 13:00 / 18:00 / 23:00`
- для дневных слотов все 5 часов — из сегодняшней даты
- для ночного слота — `23:00` вчера + `00-02` сегодня

**Сумма и разбивка:**

- карточка показывает общую сумму токенов за слот
- мини-бары под карточкой — почасовая разбивка в порядке часов слота
- для ночного слота — 4 мини-бара (`23, 00, 01, 02`); в title бара
  указана конкретная дата, чтобы было видно переход через полночь

### 6.4 Weekly Chart

График должен показывать последние 4 недели по абсолютным номерам недель:

- пример для даты `2026-08-03`: `W-29`, `W-30`, `W-31`, `W-32`

Правила отображения:

- каждая неделя отображается как отдельная группа
- внутри группы 7 столбцов: `Пн`, `Вт`, `Ср`, `Чт`, `Пт`, `Сб`, `Вс`
- текущая неделя допускается неполной
- будущие дни текущей недели не отображаются как `0`
- будущие дни текущей недели отображаются как disabled / no data yet

## 7. UX Requirements

### 7.1 Delivery Model

Продукт поставляется как один self-contained файл:

- `dashboard.html`

Файл должен открываться локально через браузер без backend-сервиса и без загрузки внешнего JSON.

### 7.2 Update Model

HTML пересобирается локально каждые 5 минут через Windows Task Scheduler.

### 7.3 Visual Direction

Dashboard должен сразу выглядеть как аккуратный визуальный артефакт, а не как технический отчёт.

Требования:

- спокойная, намеренная визуальная система
- компактный layout без лишней высоты
- основной фокус на weekly chart
- weekly chart в формате grouped bars
- группировка bars по неделям, не по дням

### 7.4 Dashboard Blocks

На первом экране должны быть:

- карточка `Токены / текущий час`
- карточка `Токены в окне {label}` где `{label}` — лейбл активного слота
  (`03:00–07:59` / `08:00–12:59` / `13:00–17:59` / `18:00–22:59` /
  `23:00–02:59`); для ночного слота подпись уточняет, что данные идут
  с 23:00 вчера по 02:59 сегодня
- полоски по часам активного слота внутри или рядом с карточкой окна
  (5 баров для дневных слотов, 4 бара для ночного)
- основной weekly chart за 4 недели

## 8. Functional Requirements

### FR-1. Static Build

Система должна иметь Python-скрипт, который генерирует полный `dashboard.html` из SQLite.

### FR-2. Local Read

Скрипт должен читать SQLite напрямую через Python `sqlite3`, без вызова внешнего `sqlite3.exe`.

### FR-3. Current Hour Card

Скрипт должен вычислять и рендерить токены за текущий календарный час в `Europe/Moscow`.

### FR-4. Active Window Card

Скрипт должен вычислять и рендерить для активного 5h-слота (см. §6.3):

- общий объём токенов в слоте
- разбивку по каждому часу слота
- лейбл слота в формате `HH:00–HH:59` в заголовке карточки
- для ночного слота — подпись `с 23:00 вчера по 02:59 сегодня`

### FR-5. Weekly Comparison Chart

Скрипт должен вычислять для последних 4 недель дневные суммы токенов и рендерить их как grouped bar chart:

- x-axis верхнего уровня: недели
- внутри каждой недели: `Пн ... Вс`

### FR-6. Future Days Rendering

Будущие дни в текущей неделе должны рендериться визуально как disabled, а не как реальный ноль.

### FR-7. Self-Contained Output

Все данные для рендера должны быть встроены в `dashboard.html`.

## 9. Non-Functional Requirements

- локальный запуск на Windows
- время сборки должно быть комфортным для запуска раз в 5 минут
- чтение должно использовать короткоживущее SQLite-соединение
- решение не должно требовать постоянного процесса в памяти
- код должен быть достаточно простым для дальнейшей доработки

## 10. Proposed Technical Design

Артефакты прототипа:

- `build_dashboard.py`
- `dashboard.html`

Поток:

1. Scheduler запускает `build_dashboard.py`
2. Скрипт читает `runtime-state.sqlite`
3. Скрипт считает агрегаты
4. Скрипт встраивает данные в HTML
5. Скрипт перезаписывает `dashboard.html`

## 11. Success Criteria

Прототип считается успешным, если:

- файл `dashboard.html` открывается локально без сервера
- данные обновляются каждые 5 минут через scheduler
- weekly chart визуально читается лучше, чем текущие CLI-отчёты
- пользователь может быстро увидеть активность по текущему часу, активному 5-часовому слоту и неделям
